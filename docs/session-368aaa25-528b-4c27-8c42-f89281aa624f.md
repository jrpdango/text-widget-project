## Findings

### P1 — correctness

1. **Deleting a widget while its create request is in flight leaves an orphan in MongoDB**
   `src/hooks/useWidgets.ts:242-317` / `:327-341`
   `deleteWidget` removes a temp widget and returns without calling the API. If the in-flight `POST` then resolves, `createFromTemp` finds no matching temp widget, so it does nothing — but the server has already created the record. Reloading brings the "deleted" widget back.
   **Fix:** mark the temp id as deleted, and when the create resolves without a surviving widget, best-effort `DELETE` the newly created server id. Add a regression test.

2. **A `404` on delete is treated as failure**
   `src/hooks/useWidgets.ts:343-365`
   If the delete succeeded server-side but the response was lost, the retry gets `404` and the widget is restored, creating a zombie. Since `DELETE` should be idempotent, treat `ApiError` with status `404` as success and do not restore.

3. **Restored widgets after a failed delete may show unsaved content as if saved**
   `src/hooks/useWidgets.ts:327-365`
   `forgetWidget` clears the pending debounce and dirty state. If the user typed within the 600 ms window and then delete failed, the restored widget shows the new text with a delete error but no pending save. Consider re-scheduling a save on restore, or explicitly marking it unsaved.

### P2 — robustness

4. **Widget routes return `500` instead of `503` after a dropped connection**
   `src/lib/db.ts:24-35`
   Once `cached.connection` is set, it is reused forever. If MongoDB later disconnects, queries fail with buffering disabled and fall into `internalError` (`500`), contradicting the README's `503 database_unavailable` contract. `pingDatabase` still reports `503`, so health and widgets disagree.
   **Fix:** only reuse the cached connection when `connection.readyState === 1`; reset stale connections/promises before reconnecting.

5. **Client does not enforce the 100,000-character limit**
   `src/components/TextWidget.tsx:67-76`, `src/lib/validation.ts:8`
   The server rejects oversized content, but the UI lets users type it and shows a retry that cannot succeed. Import `MAX_WIDGET_CONTENT_LENGTH` and pass `maxLength` to `Textarea`; optionally show `N / 100,000` in the counter.

6. **Theme effect can fight the pre-paint script during hydration**
   `src/app/layout.tsx:20-34`, `src/hooks/useTheme.ts:80-83`
   `useSyncExternalStore` hydrates with the server snapshot (`light`), then re-renders with the real client value. The follow-up effect can briefly write the stale server theme over the inline script's correct value. Worth verifying in a real browser; if it flashes, skip the first effect pass when `data-theme` is already set.

### P3 — cleanliness/readability

7. **Dead code:** `WidgetView.pendingCreate` is written but never read (`useWidgets.ts:16,22,36`). `FIXED_UPDATED_TIMESTAMP` is unused (`src/test/fixtures.ts:4`). `pingDatabase` is mocked but unused in the widget route tests.

8. **Repeated DB-connection boilerplate:** the same try/catch appears five times across `src/app/api/widgets/route.ts` and `[id]/route.ts`. Add an `ensureDatabase(): Promise<Response | null>` helper in `src/lib/http.ts` and use it in each handler.

9. **Theme key is duplicated:** `'text-widgets:theme'` is hard-coded in both `src/app/layout.tsx:22` and `src/lib/themeStorage.ts:3`. Build the inline script from `THEME_STORAGE_KEY`.

10. **Inconsistent server boundary:** `db.ts`, the model, and `serializeWidget.ts` import `server-only`, but `http.ts` and `validation.ts` do not. Add the guard to the latter two for a consistent boundary.

11. **Mixed import style:** some modules use `../lib/...`, while newer ones use `@/lib/...`. Standardise on `@/` across `src/`.

12. **Missing env ignores:** `.env*` is not in `.gitignore` or `.dockerignore`; a developer-created `.env` could be committed or copied into the Docker build context.

13. **Docs:** the API table (`README.md:101-108`) omits the `500` responses that `internalError` returns. Either document `500` or map connection errors to `503` and keep `500` for unexpected failures (both is fine).

14. **Small UX/a11y issues:** `aria-live` wraps the idle "Markdown" hint, so screen readers announce "Markdown" when a saved widget becomes idle (`TextWidget.tsx:89-106`). The footer shows "0 widgets · Stored in MongoDB" during loading/error (`App.tsx:78-82`), and the loading section has `aria-busy` but no `role="status"` (`App.tsx:35`).

15. **Optional server tuning:** add a compound index `{ createdAt: -1, _id: -1 }` for the list sort; remove the redundant `revalidate = 0` alongside `dynamic = 'force-dynamic'`; consider `poweredByHeader: false` in `next.config.ts`.

Doesn't this app still use React Compiler? Aren't all the useCallback calls unnecessary?

## Assistant

Yes — `reactCompiler: true` is still enabled in `next.config.ts`, and the production client bundle does contain compiler output (`useMemoCache`). So in the **Next production build**, the `useCallback`s are mostly redundant: the compiler memoizes functions in components and custom hooks automatically.

But they aren’t all removable *as the repo is currently configured*.

The important exception is `loadWidgets` in `src/hooks/useWidgets.ts`:

```ts
useEffect(() => {
  ...
  void loadWidgets();
  ...
}, [loadWidgets]);
```

`loadWidgets` is an effect dependency, and `vitest.config.ts` uses `react()` **without** the React Compiler option. If `loadWidgets` were a plain function, it would get a new identity every render, the effect would rerun after every render, and the test suite would refetch in a loop. In production the compiler would memoize it; in Vitest it would not.

The rest are redundant for this app:

- `persist`, `enqueueSave`, `scheduleSave`, `flushWidget`, `updateWidget`, `createFromTemp`, `addWidget`, `deleteWidget`, `retryWidget` — none are used as effect dependencies.
- No child component is wrapped in `React.memo`, so stable callback identity does not currently prevent re-renders without the compiler.
- `toggleTheme` in `useTheme.ts` likewise has no effect dependency.

They are harmless, and they do act as a safety net if React Compiler bails out on a function or is ever disabled. But if the goal is less noise, the safe cleanup is:

1. Keep `useCallback` on `loadWidgets`.
2. Convert the other callbacks to plain functions and remove their dependency arrays.
3. Re-run lint/tests — this should pass without enabling the compiler in Vitest.

The alternative is to enable React Compiler in the Vitest pipeline too (via the plugin’s compiler support, which requires an additional optional dependency) and then remove `useCallback` entirely. That makes tests exercise compiler output but adds a dependency and more moving parts.

I’d recommend option 1: strip everything except `loadWidgets`. Want me to make that cleanup?
